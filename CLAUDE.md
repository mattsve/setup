# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Ansible configuration for provisioning and managing home lab servers (Proxmox host and its LXC containers), plus an OpenTofu configuration (`tofu/`) for provisioning the Proxmox guests themselves. OpenTofu owns resource lifecycle (creating/destroying LXCs/VMs); Ansible owns in-guest configuration on top of whatever OpenTofu creates — the two don't overlap.

## Setup

```bash
ansible-galaxy collection install -r ansible/requirements.yaml
```

Requires the 1Password CLI (`op`) signed in — secrets are fetched via `community.general.onepassword` lookups in `group_vars`, not stored in the repo. `ansible/.env` holds one `PROXMOX_TOKEN_SECRET_<CLUSTER>=op://...` line per Proxmox cluster (currently `PROXMOX_TOKEN_SECRET_PVE1=op://agb/Proxmox/ansible-api-token` and `PROXMOX_TOKEN_SECRET_AGB_PVE=op://agb/Proxmox/agb-pve-ansible-api-token`), used via `op run --env-file .env -- ...`. It's checked in rather than gitignored: it only ever holds an `op://` reference, never a resolved secret, so there's nothing sensitive to keep out of the repo, and having it present on a fresh clone means a new machine just needs `op` signed in to run anything - no manual `.env` recreation step.

On macOS with Python 3.14 (Homebrew's current `ansible` formula dependency), every `ansible`/`ansible-playbook` command needs `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES` set first to avoid `ERROR! A worker was found in a dead state` — see the Troubleshooting section in the repo's `README.md` for the known upstream issue this works around.

## Commands

All commands run from the `ansible/` directory.

List discovered hosts/groups from the dynamic Proxmox inventory:
```bash
op run --env-file .env -- ansible-inventory -i inventory --list
```

Update packages on every LXC container or QEMU VM tagged `managed-updates` in Proxmox:
```bash
op run --env-file .env -- ansible-playbook playbooks/update_all_packages.yaml
```

Run a role-tagged playbook (tags: `timezone`, `nut`, `postfix`, `certbot`, `mosquitto`, `autologin`, `plex`, `caddy`, `technitium`, `pulse`, `unused_services`, `update_all_packages`, `update_cluster_nodes`) — like other playbooks, this needs the Proxmox API to discover `pve1` via the dynamic inventory, even though NUT itself connects over plain SSH:
```bash
op run --env-file .env -- ansible-playbook --tags nut playbooks/nut.yaml
```

Apply everything in one go — `playbooks/site.yaml` just `import_playbook`s every other playbook in order, purely as a convenience entrypoint; each playbook remains independently runnable as shown above:
```bash
op run --env-file .env -- ansible-playbook playbooks/site.yaml
```

## Architecture

**One dynamic inventory covers everything, one plugin file per Proxmox cluster:** `inventory/<cluster>.proxmox.yaml` (`community.proxmox.proxmox` plugin; the plugin only loads files whose name ends in `proxmox.yaml`, hence the cluster as a prefix) discovers all LXC containers, QEMU VMs, and the nodes of that cluster via its API — no `filters`/`exclude_nodes` needed. Today there are two: `pve1.proxmox.yaml` (the old single node, `pve1.management.agb.ingenstans.se`) and `agb-pve.proxmox.yaml` (the three-node `agb-pve` cluster, reached via `pve01.management.agb.ingenstans.se`, its token in the `agb-pve-ansible-api-token` field). Several files can sit side by side and Ansible merges them into one inventory, so the shared groups below (`proxmox_all_lxc`, `certbot`, ...) span every cluster; each file additionally puts its guests in a `cluster_<name>` group (via the plugin's `groups` option) so a run can be scoped with `--limit cluster_pve1`. The plugin adds *nodes* through a different code path that skips `groups`, so the nodes of each cluster are listed by hand under the same `cluster_<name>` group in `groups.yaml` (groups merge across sources) - a joining node needs a line there, unlike a guest. Each file reads its token from its own env var (`token_secret: "{{ lookup('env', 'PROXMOX_TOKEN_SECRET_PVE1') }}"`, templated by the plugin) since the plugin's built-in `PROXMOX_TOKEN_SECRET` fallback is a single name. Because the clusters merge, guest hostnames must be unique across them — a guest restored onto a new cluster while its original still exists would collapse into one inventory host. The plugin auto-creates groups per type (`proxmox_all_lxc`, `proxmox_all_qemu`, `proxmox_nodes`, etc.), and every guest (LXC or QEMU) is additionally grouped by its Proxmox tags (`proxmox_tags_<tag>`, hyphens in tag names become underscores — e.g. tag `managed-updates` → group `proxmox_tags_managed_updates`, wrapped by `managed_updates` in `groups.yaml` — see below). Results are cached (`.cache/`, jsonfile, 1h TTL) since inventory is regenerated from the API on every run. This means every playbook run needs `op run --env-file .env --` (for the `PROXMOX_TOKEN_SECRET_*` vars), even for playbooks like `nut.yaml` that only ever connect over SSH — the API is just how the host gets discovered.

**Connection vars are scoped by group, not set unconditionally.** LXC containers connect via `community.proxmox.proxmox_pct_remote` (`pct exec`, no SSH) via `inventory/group_vars/proxmox_all_lxc.yaml`; Proxmox nodes connect over SSH as root via `inventory/group_vars/proxmox_nodes.yaml` (`ansible_host` derives from `inventory_hostname`, so it generalizes to future nodes). These live in `group_vars` rather than the dynamic inventory's `compose`, which has no clean way to set a var conditionally per host type.

**Playbooks target a group instead of a boolean flag.** `inventory/groups.yaml` is a small static inventory source that exists purely to define these groups (merging into hosts discovered by the dynamic Proxmox inventory, not adding new ones):
- `postfix_relay: children: [proxmox_nodes]` — postfix relay currently applies to every Proxmox node, expressed as a child-group relationship so newly discovered nodes are included automatically, not a list that needs manual upkeep.
- `nut: hosts: [pve1]` — NUT is tied to which physical host has the USB UPS attached, which doesn't follow from any group, so it's an explicit host list.
- `managed_updates: children: [proxmox_tags_managed_updates]` — a clean alias for whichever LXC containers/QEMU VMs happen to be tagged `managed-updates` in Proxmox right now. `proxmox_tags_managed_updates` is auto-generated by the dynamic inventory's `keyed_groups` (named after the raw tag); wrapping it means the playbook targets a name defined here rather than a plugin implementation detail, and opting a guest in/out is just a Proxmox tag edit.
- `certbot: children: [proxmox_tags_certbot]` — same alias pattern as `managed_updates`: whichever guests are tagged `certbot` in Proxmox get Let's Encrypt certs.
- `mosquitto: children: [proxmox_tags_mosquitto]` — same alias pattern as `managed_updates`/`certbot`/`autologin`: deploying it is an opt-in choice (tag the guest `mosquitto` in Proxmox), not something fixed by physical hardware the way `nut` is, so new single-purpose apps like this should follow the tag pattern rather than an explicit host list — it needs no `groups.yaml` edit per new host, just a Proxmox tag.
- `autologin: children: [proxmox_tags_autologin]` — same alias pattern as `managed_updates`/`certbot`: whichever LXC containers or QEMU VMs are tagged `autologin` in Proxmox get root auto-logged-in on their console.
- `unused_services: children: [proxmox_all_lxc]` — unconditional, like `postfix_relay`: applies to every discovered LXC container, not an opt-in tag, since the stock Debian LXC template ships cron and postfix enabled by default and neither is used by this stack.
- `ssh: children: [proxmox_tags_ssh]` — same alias pattern as `certbot`/`mosquitto`/`autologin`, but as an escape hatch rather than an activation switch: `unused_services` disables sshd on every LXC container by default (Ansible reaches them via `pct exec`, not SSH), and tagging a guest `ssh` keeps it running for guests that genuinely need direct SSH access.
- `plex: children: [proxmox_tags_plex]` — same alias pattern as `certbot`/`mosquitto`/`autologin`: whichever LXC container or QEMU VM is tagged `plex` in Proxmox gets Plex Media Server installed. Can be called `plex` directly (not `plex_media`, as it once was) because the VM itself is named `plex01`, not `plex` — Ansible's hosts and groups share one namespace, and a group named the same as a host triggers `Found both group and host with same name`, which no longer applies here.
- `caddy: children: [proxmox_tags_caddy]` — same alias pattern as `mosquitto`/`plex`: the guest that runs it is named `reverse-proxy01` (a generic role name, like `mqtt01`), not `caddy` (the software, like `mosquitto`), so there's no hostname collision and the group can just be called `caddy` directly.
- `technitium: children: [proxmox_tags_technitium]` — same alias pattern as `caddy`/`plex`: the guest that runs it is named `dns01` (a generic role name), not `technitium` (the software), so there's no hostname collision and the group can just be called `technitium` directly.
- `pulse: children: [proxmox_tags_pulse]` — same alias pattern as `caddy`/`plex`/`technitium`: the guest that runs it is named `pulse01`, not `pulse`, so there's no hostname collision and the group can just be called `pulse` directly.

Each playbook then just does `hosts: <group-name>` with no `when:` gate (e.g. `postfix_relay.yaml` → `hosts: postfix_relay`, `nut.yaml` → `hosts: nut`, `update_all_packages.yaml` → `hosts: managed_updates`) — group membership *is* the switch, so there's one source of truth instead of a group plus a flag that could disagree. `timezone.yaml` is the one deliberate exception: it targets `hosts: all` directly rather than a named group in `groups.yaml`, since every host discovered by the dynamic inventory — guest or node, present or future — should be on the same clock with no opt-in step required.

**IPv6 addressing is SLAAC-derived, not Tofu-managed.** Guests don't get an explicit `ip_config.ipv6` block; they pick up an address via SLAAC from the router advertisements OPNsense sends on each VLAN (SLAAC-only, with an RDNSS option pointing at `dns01` - see below), using EUI-64 (interface ID derived from the guest's MAC), which is stable across reboots as long as the guest's `mac_address` is pinned in Tofu rather than left to Proxmox to auto-generate. OPNsense's interfaces advertise the real ISP-delegated GUA prefix (via Track Interface, so guests are dual-stacked GUA+ULA) and also a statically-assigned ULA: `fd01:eae3:bc39::/48` reserved overall, one `/64` per VLAN (below) - the ULA is what's meant to be treated as each guest's stable address, since the GUA half still moves if the ISP's delegation ever renumbers. This repo doesn't manage OPNsense, so that config and any DNS AAAA records are set by hand there, outside Ansible/Tofu.

Each VLAN gets its own `/64` off the same `/48` (matching the VLAN ID: VLAN 50 → `fd01:eae3:bc39:32::/64`), configured on OPNsense by hand - its router advertisements are SLAAC-only, with the RDNSS option pointed at `dns01` rather than OPNsense itself, so VLAN 50 hosts use Technitium as their resolver too. `dns01` (`bc:24:11:7d:cc:f0`) is on VLAN 50 (`tofu/pve1/lxc_dns.tf`'s `network_interface.vlan_id = 50`, static `10.1.50.2/24` since it can't get its own address from a DHCP service it itself provides) to run Technitium as that VLAN's DHCP server (see `technitium_dhcp_scopes` in `ansible/roles/technitium/defaults/main.yaml`) — its ULA there is `fd01:eae3:bc39:32:be24:11ff:fe7d:ccf0`. `pulse01` (`bc:24:11:f7:4b:74`) is also on VLAN 50 (`tofu/pve1/lxc_pulse.tf`), but DHCP-addressed rather than static like `dns01` - it has no such chicken-and-egg constraint, so its lease auto-registers in DNS instead (see `dnsUpdates` in the `technitium_dhcp_scopes` note above); its ULA is `fd01:eae3:bc39:32:be24:11ff:fef7:4b74`. `reverse-proxy01` (`bc:24:11:cb:ea:b5`) is on VLAN 50 too (`tofu/pve1/lxc_reverse_proxy.tf`), DHCP-addressed like `pulse01` for the same reason (no chicken-and-egg constraint); its ULA there is `fd01:eae3:bc39:32:be24:11ff:fecb:eab5`. Its friendly names (`plex.agb.ingenstans.se`, `pve.agb.ingenstans.se`, `pulse.agb.ingenstans.se`) are now CNAMEs to `reverse-proxy01.server.agb.ingenstans.se` (`host_vars/dns01.yaml`) rather than A records pointing at a fixed address, since it has none. `plex01` (`bc:24:11:82:63:3b`) is on VLAN 50 the same way; its ULA is `fd01:eae3:bc39:32:be24:11ff:fe82:633b`. `mqtt01` (`bc:24:11:42:31:c4`) is on VLAN 50 too (`tofu/pve1/lxc_mqtt.tf`), DHCP-addressed like `pulse01`/`reverse-proxy01`/`plex01` for the same reason; its ULA there is `fd01:eae3:bc39:32:be24:11ff:fe42:31c4`. Unlike those, mqtt01 isn't fronted by `caddy` (MQTT isn't HTTP) - its `mqtt.hem.ingenstans.se`/`mqtt.k3s.ingenstans.se` names are hand-managed outside this repo; `mqtt.agb.ingenstans.se` is the friendly name managed here, a CNAME into `mqtt01.server.agb.ingenstans.se` (`host_vars/dns01.yaml`), same pattern as the caddy-fronted names above.

`pve1` itself (the Proxmox host, not a guest) is on the infrastructure management VLAN (VLAN 10, `10.1.10.0/24`, gateway `10.1.10.1`; shared with switches and other infrastructure, not just Proxmox), statically addressed at `10.1.10.2` on a `vmbr0.10` VLAN sub-interface (`vmbr0` was already `bridge-vlan-aware` for guest VLAN 50 traffic, so this was a sub-interface add rather than a from-scratch VLAN-aware conversion) — unlike every guest above, this isn't Tofu-managed (Tofu only provisions guests; pve1's own `/etc/network/interfaces` is hand-edited on the host itself, done from the console/staged over SSH with console standby, precisely the risk called out in the `pulse` role note above). Its friendly name is `pve01.management.agb.ingenstans.se` (`technitium_records` in `host_vars/dns01.yaml`) — `pve01` rather than `pve1`, the same software-name-vs-host-name-shaped split as `caddy`/`reverse-proxy01`, even though here both names refer to the same physical host rather than different things. The dynamic inventory's plugin `url` (`inventory/pve1.proxmox.yaml`) and Tofu's provider `endpoint` (`tofu/pve1/provider.tf`) point directly at `pve01.management.agb.ingenstans.se`; Ansible's `ansible_host` (`group_vars/proxmox_nodes.yaml`) instead derives from `inventory_hostname` (`{{ inventory_hostname }}.management.agb.ingenstans.se`) via a `pve1.management.agb.ingenstans.se` CNAME to `pve01...` (`technitium_records` in `host_vars/dns01.yaml`) — restoring the same derive-rather-than-hardcode shape the old `.hem.ingenstans.se` suffix had, so a future second node just needs a matching CNAME, not a repo change. The old `pve1.hem.ingenstans.se` name was retired without a replacement CNAME (nothing depended on it continuing to resolve). VLAN 10 gets its own `/64` off the same `/48` as every other VLAN here (`fd01:eae3:bc39:a::/64`, hex of 10); pve1's ULA there is `fd01:eae3:bc39:a:3eec:efff:fe95:f0f8`.

One important nameserver gotcha: a client on VLAN 50 querying OPNsense's DNS resolver at any OPNsense address other than the VLAN-50-facing one (`10.1.50.1`) gets routed there fine, but the resolver replies from its VLAN-50-facing address instead of the address queried - a UDP DNS client only accepts a reply from the exact address it queried, so this silently drops as a mismatch (looks exactly like a timeout, not a refusal). `dns01`'s own resolver (`tofu/pve1/lxc_dns.tf`'s `initialization.dns.servers`) is pinned to `10.1.50.1` for this reason, rather than the datacenter-wide default nameserver.

**Secrets live in `group_vars`, not `defaults`.** Role `defaults/main.yaml` files set non-secret defaults and reference secret variables with `| default(...)` fallbacks; actual secret values are supplied in the relevant role's `inventory/group_vars/<role>.yaml` via 1Password lookups (`op://<vault>/...` — `agb` for the `Proxmox` and `dns` items, `private` for everything else). When adding a new secret-consuming role, follow this pattern (define its group in `groups.yaml`, put its secrets in `group_vars/<role>.yaml`) rather than hardcoding credentials or gating with a boolean var. `plex`'s Samba credentials (username hardcoded to `plex`, password via `op://private/l-space/plex`) follow this exact pattern in `group_vars/plex.yaml` - named after the `plex` group, since `group_vars/<name>` only loads for a group named `<name>` (see below).

**Roles** (`ansible/roles/`):
- `timezone` — sets the system timezone to `Europe/Stockholm` (`timezone_name`) via `community.general.timezone`; applied to every host via `hosts: all` (see above), not a `groups.yaml` group.
- `nut` — configures Network UPS Tools (`nut-server` + `nut-monitor`) for UPS monitoring/shutdown; installs a udev rule for the USB UPS.
- `postfix_relay` — configures Postfix to relay outbound mail through an external SMTP host (`smtp.mailbox.org` by default) using SASL auth.
- `certbot` — installs certbot + the Cloudflare DNS plugin, requests a Let's Encrypt cert per host (`certbot_domains` defaults to `<inventory_hostname>.hem.ingenstans.se`, overridable/extendable per host) via DNS-01 (no port 80/443 exposure needed), then enables certbot's own `certbot.timer` for renewal rather than an Ansible-managed cron job.
- `mosquitto` — installs the Mosquitto MQTT broker with persistence enabled and two listeners: a TLS listener (`mosquitto_tls_port`, default 8883) and a plaintext listener (`mosquitto_plain_port`, default 1883) kept alongside it for units that don't support TLS. Consumes the cert the `certbot` role already requested for this host, but copies it into `/etc/mosquitto/certs` rather than pointing the listener at `/etc/letsencrypt/live/...` directly, since that live path is a symlink into `/etc/letsencrypt/archive`, which is `0700 root` and not traversable by the unprivileged `mosquitto` user. The role also drops its own script into certbot's `/etc/letsencrypt/renewal-hooks/deploy/` so the copy gets refreshed (and mosquitto restarted) after every renewal — `certbot` doesn't need to know mosquitto exists; any future cert consumer plugs into that same hook directory rather than the certbot role growing per-consumer logic. `mosquitto_tls_enabled` derives from `'certbot' in group_names` rather than a separate flag, so a host that isn't in the `certbot` group (no cert to serve) automatically falls back to plaintext-only instead of failing on a missing cert file. Client auth is opt-in via `mosquitto_users` (empty by default), a list of `{username, password}` maps built in `group_vars/mosquitto.yaml` from a single 1Password item ("mqtt-users", a Secure Note) rather than one 1Password item per user like `plex`'s Samba credentials: each user is one custom password-type field on that item, field label as the username and field value as the password, fetched via `community.general.onepassword_raw`, filtered to fields where `type == 'CONCEALED'` and no `purpose` (excludes any built-in fields a non-Secure-Note item type would carry), and turned into the list with `map`/`zip`/`dict`/`dict2items` rather than a Python-style comprehension (Jinja has no such syntax) - adding/removing a user is then a 1Password-only edit, no repo change. No community.general module wraps Mosquitto's own `mosquitto_passwd` CLI tool (it ships with the `mosquitto` package itself, no extra install needed), so the role calls it directly via `command` against a `password_file` (`mosquitto_passwd_file`) - but only for users not already present (checked with a `grep` per user first), since the tool's own hashing is randomly salted PBKDF2-SHA512 and would report changed on every run otherwise; this means a password *rotation* in the 1Password item isn't picked up automatically, only a new user being added. `mosquitto_allow_anonymous` is deliberately kept a manual flag rather than derived from `mosquitto_users` like `mosquitto_tls_enabled` is from group membership: deriving it would lock out any anonymous client the moment the first user is added, so it's left `true` until flipped by hand once every client in use has been migrated to credentials.
- `autologin` — drops a systemd override (`ExecStart=` reset + `agetty --autologin root`) on the guest's tty1 getty unit, restarting it on change so it takes effect without a reboot. Which unit that is depends on guest type (`autologin_getty_unit`, derived from `'proxmox_all_qemu' in group_names` rather than a separate flag, same pattern as `mosquitto_tls_enabled`): LXC containers under systemd use `container-getty@1.service` — what `pct console` attaches to — while QEMU VMs use the plain `getty@tty1.service` a bare-metal host would. Only ever overrides `container-getty@1`/`getty@tty1` (the primary console); other gettys spawned on a guest (e.g. `container-getty@2` for a second configured tty, or `console-getty.service` on LXC's `/dev/console`) are untouched and still prompt for login.
- `unused_services` — disables and stops `cron` and `postfix` on every LXC container (stock Debian template services this stack never uses — mail relaying is `postfix_relay`'s job on `proxmox_nodes`, not here), plus `sshd` unless the guest is tagged `ssh` (`unused_services_keep_ssh`, derived from `'ssh' in group_names` rather than a separate flag, same pattern as `mosquitto_tls_enabled`/`autologin_getty_unit`) — Ansible reaches LXCs via `pct exec`, never SSH, so a listening sshd is unused attack surface by default.
- `plex` — mounts the `//files.agb.ingenstans.se/data/media` Samba share read-only at `/mnt/media` (credentials templated into a root-only `/etc/samba/credentials-media` file, referenced from the `_netdev` fstab entry rather than embedded inline), then installs Plex Media Server from its official apt repo (`repo.plex.tv`, signed by the `PlexSign.v2.key` - the original `downloads.plex.tv`/`PlexSign.key` pairing is deprecated and its key carries a SHA1 binding signature that Debian trixie's `sqv` verifier rejects under the post-2026-02-01 crypto policy) via `deb822_repository` (key fetched straight from `plex_apt_key_url` and dearmored by the module itself, no manual `gpg --dearmor` step), and enables/starts the `plexmediaserver` service. No config templating for Plex itself: it's set up and claimed through its own web UI, not a static config file Ansible would own.
- `caddy` — reverse proxy for web UIs on non-standard ports, installed from Caddy's official apt repo (`dl.cloudsmith.io/public/caddy/stable`, same `deb822_repository` pattern as `plex`). Routes are driven entirely by `caddy_proxies`, a list of `{hostname, backend, backend_scheme, backend_tls_insecure}` maps supplied per host (`host_vars/reverse-proxy01.yaml`), templated into one vhost block per entry in `/etc/caddy/Caddyfile`; `backend_scheme`/`backend_tls_insecure` exist because some backends (e.g. Proxmox's own web UI on 8006) are HTTPS-only with a self-signed cert, unlike the plain-HTTP default. Consumes a single wildcard cert (`certbot_domains: ["hem.ingenstans.se", "*.hem.ingenstans.se"]`, overridden in `host_vars/reverse-proxy01.yaml` since the role default is one name per host) covering every vhost it fronts, copied into `/etc/caddy/certs` and refreshed via a certbot renewal hook — the same cert-handoff pattern `mosquitto` uses, chosen so adding a new proxied hostname is just a `caddy_proxies` edit, never a cert request. The guest itself is named `reverse-proxy01` rather than `caddy`, following the `mqtt01`/`mosquitto` split (generic role name for the host, software name for the tag/group) — see `caddy` in `groups.yaml` above.
- `technitium` — installs Technitium DNS Server by fetching and running its official install script (`technitium_install_script_url`, `download.technitium.com/dns/install.sh`) rather than the `deb822_repository` pattern `plex`/`caddy` use, since Technitium doesn't publish an apt repo. The script is re-run unconditionally on every play (`force: true` on the `get_url`, no `creates` guard on the `command`) rather than gated on a one-time install check, because Technitium's own docs treat re-running this same script as the update mechanism: it always pulls the latest DNS server tarball, and once `/etc/dns/config` exists it just re-extracts, re-`chown`s, and `systemctl restart dns.service`s, skipping the one-time `useradd`/systemd-unit/`NetworkManager` setup from a fresh install. There's no version file or diffing in the script (or anywhere else) to check "is a newer release available" without actually re-running it, so every play run restarts `dns.service` regardless of whether a new version actually shipped — the cost of upgrades actually flowing through the playbook rather than needing a manual login to the web console. The guest is named `dns01` rather than `technitium`, following the `mqtt01`/`mosquitto` split — see `technitium` in `groups.yaml` above. `dns01` is still tagged `managed-updates` like every other guest: that only covers apt-based OS package bumps via `update_all_packages.yaml`, a separate channel from Technitium's own version, which is upgraded by this role on every play. Unlike `plex`, zone/record data *is* Ansible-managed here — DNS was judged too important to leave to manual console edits. The role uses the third-party `effectivelywild.technitium_dns` collection's state-based `technitium_dns_zone`/`technitium_dns_record` modules (idempotent `state: present`/`absent`, not the collection's other imperative `create_zone`/`add_record`-style modules) against Technitium's REST API on `localhost:5380` (tasks run on `dns01` itself via `pct exec`, so `localhost` always resolves correctly regardless of the guest's address). Desired zones/records are supplied per host in `host_vars/dns01.yaml` as `technitium_zones`/`technitium_records` lists of arbitrary API-param maps, merged over `{api_url, api_token, state: present}` defaults with `combine` in `tasks/main.yaml` rather than the role enumerating every record type's fields itself — the same "let the caller's dict shape drive the module call" approach as `caddy_proxies`, chosen because the record module alone has ~30 type-specific optional params (`ipAddress`, `cname`, `exchange`, ...). Authentication is a pre-generated API token (`technitium_api_token`), not a username/password the role logs in with — generate it once via the web console (Administration > Sessions > Create Token) and store it in 1Password, since this repo's convention is that Ansible consumes pre-existing secrets, never generates them itself. DNS Apps (Technitium's plugin system, e.g. Query Logs) are likewise Ansible-managed rather than console-installed, via `technitium_apps` (per-host `{name, url}` maps in `host_vars/dns01.yaml`, same `combine`-over-defaults shape as `technitium_zones`/`technitium_records`/`technitium_dhcp_scopes`). Installing and updating are two different collection modules run back to back over the same list (`technitium_dns_download_and_install_app`, which no-ops on an already-installed name rather than updating it, then `technitium_dns_download_and_update_app`, which would otherwise fail against a name that isn't installed yet) — no `when:` needed between them, since the install task guarantees every app exists by the time the update task runs, whether it just installed it or it was already there. A version bump is then just editing the pinned url in `technitium_apps` and re-running the play, same as everything else here. DNS-based blocking (ads/trackers/malware) is likewise Ansible-managed: `technitium_block_list_urls` (per-host, `host_vars/dns01.yaml`, currently the HaGeZi Pro list) feeds `technitium_dns_set_server_settings`'s `blockListUrls`, alongside `blockingType: NxDomain` (a blocked query returns "domain doesn't exist" rather than a placeholder address, so it behaves correctly for every record type) and a `technitium_blocking_bypass_list` of client IPs exempt from blocking entirely. `technitium_blocking_enabled` (→ `enableBlocking`) derives from whether there's anything to block (`technitium_block_list_urls`/`technitium_blocked_zones` non-empty) rather than a separate manual flag, same pattern as `technitium_tls_enabled`. `blockListUrls` can't be cleared by passing an empty list (the module rejects that outright) — going back to zero block lists needs the explicit `clear_blockListUrls` flag instead, which the role derives the same way. Per-domain overrides (`technitium_blocked_zones`/`technitium_allowed_zones`, both empty by default) go through the collection's imperative `technitium_dns_add_blocked_zone`/`technitium_dns_add_allowed_zone` modules rather than a state-based one like `technitium_dns_zone` — no such module exists for these, so they're add-only: removing a domain from either list here doesn't un-block/un-allow it on the server, that still needs a manual console edit or the collection's `delete_blocked_zone`/`delete_allowed_zone` run by hand. The whole role runs under the single `technitium` tag like every other role here, but its own `tasks/main.yaml` additionally tags each logical section (`technitium_install`, `technitium_cert`, `technitium_tls_settings`, `technitium_zones`, `technitium_records`, `technitium_dnssec`, `technitium_blocking`, `technitium_dhcp`, `technitium_apps`) so a slow full run isn't the only option — e.g. `--tags technitium_records` to push just a record change, or `--skip-tags technitium_install` to skip the unconditional install-script re-run (the slowest step, since it always re-extracts the tarball and restarts `dns.service`) when iterating on something else.

**Technitium API calls go over HTTPS from the controller, not through `pct exec`.** Once a host has TLS (`technitium_api_remote`, derived from `technitium_tls_enabled`), every API task after the TLS-settings task is wrapped in one block that sets `delegate_to: localhost`, `become: false`, and points `technitium_api_url`/`technitium_api_port` at `https://<technitium_node_domain>:53443`. A `pct exec` per record (connection + module transfer each) made the record loop take minutes; one HTTPS request each is seconds. The TLS-settings task itself stays on `http://localhost:5380` inside the guest since it is what turns HTTPS on, and a host without TLS falls back to localhost for everything. Needs the controller to reach port 53443 (main VLAN only, per the firewall) and to resolve the node's `*.server.agb.ingenstans.se` name; the node name rather than `technitium_domain` is used because the latter can be the cluster domain, which has no apex records.

**Technitium clustering (dns01 primary, dns02 secondary).** `technitium_cluster_role` (`primary`/`secondary`, empty = standalone; `host_vars/dns01.yaml`, `dns02.yaml`) drives a cluster section at the end of the role's tasks: set `dnsServerDomain`, then init (primary) and join (secondary) as two consecutive tasks so the linear strategy guarantees the primary is ready first. Both are guarded by `get_cluster_state`, so re-runs are no-ops. The primary owns all config; every zone/record/DNSSEC/blocking/DHCP/app task is skipped on a secondary (`technitium_manage_config`), since the join overwrites those from the primary. The join takes an admin username/password (`group_vars/technitium.yaml`, `op://agb/dns/username|password`), not an API token. dns02 has its own API token (`op://agb/dns/dns02-ansible-api-token`), created on its console before the first join. Cluster traffic is VLAN 50 to VLAN 50, so it never transits OPNsense and needs host firewall rules for 53443 on both guests (`firewall_dns.tf`, `dns02.tf`). DHCP is not clustered, so dns02 serves none.

`dns01` is also tagged `certbot` (`tofu/pve1/lxc_dns.tf`) so Technitium can terminate TLS itself rather than sitting behind `caddy` the way every other web UI here does: DNS-over-TLS is raw TLS-wrapped DNS on its own port, not HTTP, so a reverse proxy in front of it couldn't terminate it anyway, and once Technitium needs its own cert for that, the web console piggybacks on the same one instead of splitting TLS termination across two different services. `host_vars/dns01.yaml` overrides `certbot_domains` to cover both names dns01 is reachable as: the friendly `dns.agb.ingenstans.se` (hardcoded rather than built from `inventory_hostname` — same generic-service-name-vs-host-name split as `caddy`/`reverse-proxy01` and `plex`/`plex01` — and the one `technitium_domain` points `--cert-name`'s lineage at) and `dns01.server.agb.ingenstans.se` (its own already-existing static record), ahead of the certbot role's plain `dns01.hem.ingenstans.se` default — matching `reverse-proxy01`'s earlier move to the newer domain. Both validate through the same Cloudflare DNS-01 challenge: Cloudflare's only zone here is `ingenstans.se` itself — there's no separate `agb.ingenstans.se` or `server.agb.ingenstans.se` zone — and `dns.agb.ingenstans.se`/`dns01.server.agb.ingenstans.se` are both just subdomains of it, not delegated elsewhere, so Cloudflare is the public authority for the challenge TXT record on either. That's the split-horizon property the whole setup relies on: Cloudflare stays authoritative for the public DNS-01 lookup across all of `ingenstans.se`, while the same-named Primary zones inside Technitium (`technitium_zones` below) independently serve different, internal-only answers for specific names — the two are resolved through entirely separate paths (Cloudflare's public nameservers vs. Technitium's API) and never conflict. A `dns.agb.ingenstans.se` CNAME (`technitium_records`, into `dns01.server.agb.ingenstans.se`) makes the friendly name resolve internally too, same pattern as the `plex`/`pve`/`pulse` friendly names. Technitium takes its cert as a single PKCS#12 (`.pfx`) bundle rather than the separate `fullchain.pem`/`privkey.pem` copies `mosquitto`/`caddy` use, so a `command`-run `openssl pkcs12 -export` (no `creates` guard, same reasoning as certbot's own cert-request task) rebuilds it from certbot's live PEM output on every play, and a certbot deploy hook rebuilds it again on renewal. The `.pfx` password (`technitium_pfx_password`) is deliberately hardcoded empty rather than pulled from 1Password: the file is only ever read by Technitium's own `dns-server` service user off a `0600` path, so the filesystem permissions are what actually protect it, the same as `mosquitto`/`caddy`'s unencrypted private key copies — PKCS#12 just requires *a* password syntactically. `technitium_dns_set_server_settings` then points the web console (`webServiceTlsPort`, 53443) and both DNS-over-TLS (853) and DNS-over-HTTPS (443) at that same bundle in one API call, plus turns on `dnssecValidation` so Technitium validates DNSSEC on the upstream/recursive answers it forwards. Zone signing is separate from that call: `technitium_dns_sign_zone` "will not update DNSSEC properties once initially signed" and errors on a zone that's already signed, so the role first calls `technitium_dns_get_dnssec_properties` per zone in `technitium_dnssec_zones` (`host_vars/dns01.yaml`) and only signs the ones still `Unsigned` — ECDSA/P256 by default, chosen as the modern, widely-supported, low-overhead choice over RSA. `hem.ingenstans.se` is deliberately left unsigned (it's being retired, though still served for backwards compatibility, per the zone comment in `host_vars/dns01.yaml`); none of the signed zones are delegated to `dns01` from a real parent zone (they're all internal-only), so signing them doesn't build a chain of trust an external resolver could follow — its value here is a validating client on VLAN 50 being able to detect a tampered/spoofed answer, not public verifiability. `tofu/pve1/firewall_dns.tf` locks `dns01` down to a default-deny inbound Proxmox firewall (it previously had none at all, unlike `pulse01`'s), but only scopes one thing at the host level: which VLANs can reach `dns01` at all is OPNsense's job now (inter-VLAN policy lives there, hand-managed, not duplicated per-guest in Tofu), so plain DNS (53), DNS-over-TLS (853), DNS-over-HTTPS (443), and DHCP (67) are accept-from-anywhere rules with no `source` restriction — the DHCP rule alone covers both VLAN 50's direct clients (pre-lease broadcast DHCPDISCOVERs at `0.0.0.0` included) and VLAN 80's relayed requests (arriving unicast from OPNsense's relay agent, see below), since neither needs special-casing once source isn't filtered at all. The web console (53443) is the deliberate exception, narrowed to main (VLAN 100, `10.1.100.0/24`) only rather than opened up like the rest — not even VLAN 50, despite `dns01` living there — because it's the one rule that can't move to OPNsense: `dns01` sits on VLAN 50 itself, so VLAN 50-sourced traffic to it never transits OPNsense, and only a host-level rule can keep VLAN 50 off the console while every VLAN still gets DNS/DHCP. That console rule has a second, IPv6 counterpart scoped to the main ULA `/64` (`fd01:eae3:bc39:64::/64`) rather than its GUA range, since Proxmox's firewall won't let one rule's `source` list mix address families. ULA rather than GUA because RDNSS hands clients dns01's ULA as their resolver (see above), and Linux's kernel-level IPv6 source-address-selection already has a distinct label for `fc00::/7` separate from the default (GUA) label, so a connection to a ULA destination reliably sources from ULA too (confirmed against `firewall_pulse.tf`'s existing ULA-pinned rule, which depends on the same behavior) — no equivalent GUA allow is needed, and hardcoding one would be fragile anyway since the GUA half can renumber. DHCP is served directly to VLAN 50 clients rather than relayed, since dns01 sits on VLAN 50 itself — relaying within the same subnet was tried once via OPNsense's IP Helper and broke mqtt01's lease, so that's off now.

VLAN 80 (IoT, `10.1.80.0/24`) is relayed instead, since dns01 doesn't sit on that VLAN — genuine cross-subnet relay, not the same-subnet case above. A relayed request arrives unicast from OPNsense's VLAN 80 interface (the relay agent) rather than from the client's own address, but `tofu/pve1/firewall_dns.tf`'s DHCP rule doesn't need to special-case that source any more than it does VLAN 50's — it accepts DHCP from anywhere, same as DNS/DoT/DoH, and leaves reachability to OPNsense. The `iot` scope (`technitium_dhcp_scopes` in `host_vars/dns01.yaml`) mirrors the `server` scope's shape (`.50`-`.250`, `.2`-`.49` held back for static/infra) but registers into its own `iot.agb.ingenstans.se` zone rather than `server.agb.ingenstans.se`, keeping IoT leases out of the general-server namespace. The web console stays main-only regardless, so VLAN 80 doesn't get it either, same as VLAN 50. OPNsense's VLAN 80 interface, its IPv6 `/64`, and the DHCP relay (IP Helper, pointed at dns01's `10.1.50.2`) are configured by hand there, outside this repo, same as every other VLAN's OPNsense-side config described above.
- `pulse` — installs Pulse (rcourtman/Pulse, a Proxmox/Docker/Kubernetes monitoring dashboard) via its official install script (`pulse_install_script_url`, `raw.githubusercontent.com/rcourtman/Pulse/main/install.sh`), guarded by a `stat` check on `/bin/update` so it only runs on a genuinely fresh install, unlike `technitium`'s unconditional-rerun pattern. Re-running is deliberately *not* how this role keeps Pulse current: `/bin/update` prompts via `/dev/tty` directly (bypassing stdin redirection entirely) whenever it's ambiguous whether to reinstall an already-up-to-date install, and since `pct exec` always provides a real pty, that read never gets an EOF and just hangs forever with no flag to force past it - unlike Technitium's install script, which has no such interactive case. Pulse's own installer already sets up a `pulse-update.timer` (daily, 2-6 AM) that keeps it current on its own, so this role leans on that instead - the same "install once, let the software's own timer own renewal" shape `certbot` uses in this repo. The installer's own defaults (service name `pulse`, port 7655) are used as-is, no config templating. Previously run by hand directly on `pve1` rather than in a dedicated guest; moved into its own LXC (`pulse01`, VLAN 50, DHCP-addressed) both to bring it in line with every other service here and because giving something running directly on the hypervisor a VLAN address would mean tagging `pve1`'s own host networking, which risks its management connectivity - a guest is the safe way to get a service onto a given VLAN. (`pve1` itself has since moved onto the infrastructure management VLAN — see the IPv6/VLAN addressing note below.)
- `proxmox_node_update` — rolling update of the `agb-pve` nodes (`playbooks/update_cluster_nodes.yaml`, `hosts: cluster_agb_pve:&proxmox_nodes`, `serial: 1`; the intersection is needed because `cluster_agb_pve` also holds that cluster's guests, and the role counts nodes via `ansible_play_hosts_all`; `pve1` is excluded since it's standalone with no HA to evacuate to). Per node: health gate (quorate, all nodes online, HA services settled, replication jobs error-free and synced within `proxmox_node_update_replication_max_age`; stale non-failing jobs are kicked with `schedule_now` rather than waiting out their interval) -> `apt dist-upgrade` -> reboot check (`/var/run/reboot-required` *or* running kernel != newest `/boot/vmlinuz-*`, since Proxmox kernels don't reliably set the former) -> if needed, `ha-manager crm-command node-maintenance enable`, wait until no non-idle HA service is on the node, reboot, wait for health, `node-maintenance disable` -> same health gate again before the next node (so a node never goes down while a replica is stale). Maintenance mode only evacuates HA guests, so it aborts if a running guest isn't HA-managed (`proxmox_node_update_allow_non_ha_guests` to override). On any failure the node is deliberately left in maintenance rather than auto-undone. Separate from `update_all_packages.yaml`, which covers guests.

`nut`, `postfix_relay`, `mosquitto`, `autologin`, and `caddy` follow the same shape: `defaults/main.yaml` (config vars), `tasks/main.yaml` (install package → template configs, each notifying a handler → enable/start service), `handlers/main.yaml` (restart-on-change), `templates/*.j2` (config files rendered from vars). `pulse` has a handler (`Restart Pulse`, notified when its `/etc/pulse/.env` override changes - e.g. `PULSE_TELEMETRY=false`) but no templates: that file is a single `lineinfile` edit into a hook the installed unit already provides (`EnvironmentFile=-/etc/pulse/.env`), not a Jinja template Ansible owns the whole content of. `certbot`, `unused_services`, `plex`, `technitium`, and `timezone` have no handler or templates: `certbot` because nothing needs restarting on cert issuance/renewal (the standalone timer owns renewal); `unused_services` because it only flips `state`/`enabled` on services that are already installed by the base template, with nothing to render; `plex` because there's no Ansible-managed config file to change, just an install step and a service enable; `technitium` because its zone/record state lives behind a REST API, not a config file Ansible would template and reload; `timezone` because it's a single module call with no config file or service to restart.

## OpenTofu (`tofu/`)

Provider: `bpg/proxmox`, authenticating with its own `root@pam!opentofu` API token — separate from the `root@pam!ansible` token the Ansible inventory uses, so the two tools don't share credentials (same Proxmox host as the inventory). **One directory per Proxmox cluster**, `tofu/<cluster>/`, each a self-contained root module with its own provider endpoint, `.env`, lock file and local state - so clusters never share state, and retiring one is just deleting its directory. Today that is `tofu/pve1/` (the old single node, endpoint `pve1.management.agb.ingenstans.se`; the guest files named below all live there) and `tofu/agb-pve/` (the three-node cluster, endpoint `pve01.management.agb.ingenstans.se`, token in the `agb-pve-opentofu-api-token` field). `agb-pve/` holds its SDN config (`sdn.tf`), the shared container template download (`templates.tf`), and its guests. Containers are one small file per guest (e.g. `dns02.tf`) calling `modules/ha_container`, which bundles the container, its Proxmox firewall (default-deny inbound plus an `firewall_rules` allow-list), ZFS replication jobs, the HA resource and its node-affinity rule - so adding a container is one file of inputs, not several files of repeated resources. (VMs differ enough that they'll get their own module rather than stretching this one.) The SDN config is a VLAN zone `vlans` on `vmbr1` with VNets `server` (VLAN 50) and `mgmt` (VLAN 10) for guests to attach to by name instead of `vmbr0` + `vlan_id`. `vmbr1` sits on `nic1` (a switch trunk port) and, like the management network, is hand-configured identically on every node rather than through Tofu: an address-less, VLAN-aware bridge, while `vmbr0` (`nic0`, cluster/corosync + management VLAN 10) is restricted to `bridge-vids 10` so guests can't be placed on other VLANs through it. SDN provides only named, tagged networks - no subnets/IPAM/DHCP, since OPNsense and Technitium own routing, RA and DHCP. Zone/VNet IDs are capped at 8 characters.

**HA-managed guests and Tofu (`agb-pve/` only; needs provider >= 0.117, pinned in its `versions.tf`).** Guests there are replicated over ZFS (`proxmox_replication`, no shared storage) and run under HA (`proxmox_haresource` + a `proxmox_harule` node-affinity rule, since PVE 9 replaced HA groups with rules). HA, not Tofu, decides where such a guest runs, so its `node_name` is only the creation node: `modules/ha_container` sets `lifecycle { ignore_changes = [node_name] }` on the container and `ignore_changes = [target]` on the replication jobs (Proxmox rewrites a job's target when the guest moves, since a job can't replicate to its own node). Found by putting a node into maintenance and planning: before provider 0.115 a container HA had moved was dropped from state and planned as a bare create (a duplicate VM ID); from 0.115 it is found on its real node but a `node_name` mismatch plans a destroy-and-recreate (`migrate = true` would migrate instead, but we don't want Tofu moving HA guests). The module also sets the root disk's `replicate = true` - the provider's default is `false`, which excludes the rootfs from replication jobs. A manual `ha-manager migrate` to a lower-priority node is refused ("not allowed on target node"); to test failover use `ha-manager crm-command node-maintenance enable <node>` (and `disable` after). Nothing is shared between cluster directories yet - a `tofu/modules/` only makes sense once two clusters genuinely share code. Run commands from the cluster's directory:

```bash
op run --env-file .env -- tofu plan
op run --env-file .env -- tofu apply
```

`tofu/pve1/.env` holds `TF_VAR_proxmox_token_secret=op://agb/Proxmox/opentofu-api-token` (a field on the same `Proxmox` 1Password item Ansible's secrets live on, alongside `ansible-api-token`) - checked in for the same reason as `ansible/.env` above, since it's just an `op://` reference. `provider.tf` builds the full `api_token` string (`user!tokenid=secret`) from that var; only the secret half (resolved by `op run` at runtime, never written to disk) is out of tree.

The `opentofu` token needs more than the `PVEAdmin` role, so it also holds one small custom role, `OpenTofu` (`Sys.AccessNetwork` + `Sys.Modify`), granted alongside `PVEAdmin` at `/` (propagated) rather than handing out `Administrator`. Two things need it: any resource that downloads by URL (e.g. `proxmox_download_file`, used for CT templates) calls Proxmox's `query-url-metadata` endpoint, which requires `Sys.AccessNetwork`; and setting a QEMU VM's `startup` block requires `Sys.Modify`, checked at `/` specifically (so a `/nodes`-scoped grant wouldn't satisfy it). Neither is covered by `PVEAdmin` or any built-in role short of full `Administrator`. One role granted at `/`, not two roles at different paths, because `Sys.*` privileges are only ever checked on `/` and `/nodes/<node>` — granting `Sys.AccessNetwork` at `/` gives nothing extra on storage, VM or pool paths. The `ansible` token, by contrast, only reads (the dynamic inventory lists guests) and holds just `PVEAuditor`. Both tokens are created with privilege separation on; the commands to recreate them and their ACLs are in `README.md`'s "Proxmox API access" and "OpenTofu" sections.

State is local (`terraform.tfstate`, gitignored) — deliberate for a single-operator, single-machine homelab: local state avoids standing up a remote backend to solve a locking problem that doesn't exist here. The tradeoff is that state isn't backed up independently of this repo's `tofu/<cluster>/` directories; if this machine is lost with no backup, the Proxmox resources OpenTofu created keep running untouched, but reattaching them requires `tofu import` per resource. `.terraform.lock.hcl` **is** committed (pins provider version/hashes); `.terraform/` and `*.tfstate*` are not.

`vm_ha.tf` (Home Assistant OS, VM 101 `ha`) and `vm_pbs.tf` (Proxmox Backup Server, VM 102 `pbs01`) are the two guests Tofu *adopts* rather than creates: both predate Tofu here (`ha` was built on an earlier system and migrated, `pbs01` was installed by hand from the PBS ISO), so there's no source image to `import_from`. Each was brought in with `tofu import` (e.g. `proxmox_virtual_environment_vm.ha pve1/101`) purely to document its settings and surface drift in `tofu plan`. `prevent_destroy` and `ignore_changes` on their disks are deliberate - don't "fix" them by adding an image; recreating either means restoring from backup, not applying Tofu. Neither is tagged `managed-updates` (HAOS isn't apt-based, and Ansible doesn't configure either of them).
