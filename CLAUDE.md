# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Ansible configuration for provisioning and managing home lab servers (Proxmox host and its LXC containers), plus an OpenTofu configuration (`tofu/`) for provisioning the Proxmox guests themselves. OpenTofu owns resource lifecycle (creating/destroying LXCs/VMs); Ansible owns in-guest configuration on top of whatever OpenTofu creates — the two don't overlap.

## Setup

```bash
ansible-galaxy collection install -r ansible/requirements.yaml
```

Requires the 1Password CLI (`op`) signed in — secrets are fetched via `community.general.onepassword` lookups in `group_vars`, not stored in the repo. `ansible/.env` (gitignored) holds `PROXMOX_TOKEN_SECRET`, used via `op run --env-file .env -- ...`.

On macOS with Python 3.14 (Homebrew's current `ansible` formula dependency), every `ansible`/`ansible-playbook` command needs `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES` set first to avoid `ERROR! A worker was found in a dead state` — see the Troubleshooting section in the repo's `README.md` for the known upstream issue this works around.

## Commands

All commands run from the `ansible/` directory.

List discovered hosts/groups from the dynamic Proxmox inventory:
```bash
op run --env-file .env -- ansible-inventory -i inventory --list
```

Update packages on every LXC container or QEMU VM tagged `managed-updates` in Proxmox:
```bash
op run --env-file .env -- ansible-playbook playbooks/update_all_packages.yaml
```

Run a role-tagged playbook (tags: `timezone`, `nut`, `postfix`, `certbot`, `mosquitto`, `autologin`, `plex`, `caddy`, `technitium`, `pulse`, `unused_services`, `update_all_packages`) — like other playbooks, this needs the Proxmox API to discover `pve1` via the dynamic inventory, even though NUT itself connects over plain SSH:
```bash
op run --env-file .env -- ansible-playbook --tags nut playbooks/nut.yaml
```

Apply everything in one go — `playbooks/site.yaml` just `import_playbook`s every other playbook in order, purely as a convenience entrypoint; each playbook remains independently runnable as shown above:
```bash
op run --env-file .env -- ansible-playbook playbooks/site.yaml
```

## Architecture

**One dynamic inventory covers everything:** `inventory/proxmox.yaml` (`community.proxmox.proxmox` plugin) discovers all LXC containers, QEMU VMs, and the node itself on the Proxmox host at `pve1.hem.ingenstans.se` via its API — no `filters`/`exclude_nodes` needed. The plugin auto-creates groups per type (`proxmox_all_lxc`, `proxmox_all_qemu`, `proxmox_nodes`, etc.), and every guest (LXC or QEMU) is additionally grouped by its Proxmox tags (`proxmox_tags_<tag>`, hyphens in tag names become underscores — e.g. tag `managed-updates` → group `proxmox_tags_managed_updates`, wrapped by `managed_updates` in `groups.yaml` — see below). Results are cached (`.cache/`, jsonfile, 1h TTL) since inventory is regenerated from the API on every run. This means every playbook run needs `op run --env-file .env --` (for `PROXMOX_TOKEN_SECRET`), even for playbooks like `nut.yaml` that only ever connect over SSH — the API is just how the host gets discovered.

**Connection vars are scoped by group, not set unconditionally.** LXC containers connect via `community.proxmox.proxmox_pct_remote` (`pct exec`, no SSH) via `inventory/group_vars/proxmox_all_lxc.yaml`; Proxmox nodes connect over SSH as root via `inventory/group_vars/proxmox_nodes.yaml` (`ansible_host` derives from `inventory_hostname`, so it generalizes to future nodes). These live in `group_vars` rather than the dynamic inventory's `compose`, which has no clean way to set a var conditionally per host type.

**Playbooks target a group instead of a boolean flag.** `inventory/groups.yaml` is a small static inventory source that exists purely to define these groups (merging into hosts discovered by the dynamic Proxmox inventory, not adding new ones):
- `postfix_relay: children: [proxmox_nodes]` — postfix relay currently applies to every Proxmox node, expressed as a child-group relationship so newly discovered nodes are included automatically, not a list that needs manual upkeep.
- `nut: hosts: [pve1]` — NUT is tied to which physical host has the USB UPS attached, which doesn't follow from any group, so it's an explicit host list.
- `managed_updates: children: [proxmox_tags_managed_updates]` — a clean alias for whichever LXC containers/QEMU VMs happen to be tagged `managed-updates` in Proxmox right now. `proxmox_tags_managed_updates` is auto-generated by the dynamic inventory's `keyed_groups` (named after the raw tag); wrapping it means the playbook targets a name defined here rather than a plugin implementation detail, and opting a guest in/out is just a Proxmox tag edit.
- `certbot: children: [proxmox_tags_certbot]` — same alias pattern as `managed_updates`: whichever guests are tagged `certbot` in Proxmox get Let's Encrypt certs.
- `mosquitto: children: [proxmox_tags_mosquitto]` — same alias pattern as `managed_updates`/`certbot`/`autologin`: deploying it is an opt-in choice (tag the guest `mosquitto` in Proxmox), not something fixed by physical hardware the way `nut` is, so new single-purpose apps like this should follow the tag pattern rather than an explicit host list — it needs no `groups.yaml` edit per new host, just a Proxmox tag.
- `autologin: children: [proxmox_tags_autologin]` — same alias pattern as `managed_updates`/`certbot`: whichever LXC containers or QEMU VMs are tagged `autologin` in Proxmox get root auto-logged-in on their console.
- `unused_services: children: [proxmox_all_lxc]` — unconditional, like `postfix_relay`: applies to every discovered LXC container, not an opt-in tag, since the stock Debian LXC template ships cron and postfix enabled by default and neither is used by this stack.
- `ssh: children: [proxmox_tags_ssh]` — same alias pattern as `certbot`/`mosquitto`/`autologin`, but as an escape hatch rather than an activation switch: `unused_services` disables sshd on every LXC container by default (Ansible reaches them via `pct exec`, not SSH), and tagging a guest `ssh` keeps it running for guests that genuinely need direct SSH access.
- `plex: children: [proxmox_tags_plex]` — same alias pattern as `certbot`/`mosquitto`/`autologin`: whichever LXC container or QEMU VM is tagged `plex` in Proxmox gets Plex Media Server installed. Can be called `plex` directly (not `plex_media`, as it once was) because the VM itself is named `plex01`, not `plex` — Ansible's hosts and groups share one namespace, and a group named the same as a host triggers `Found both group and host with same name`, which no longer applies here.
- `caddy: children: [proxmox_tags_caddy]` — same alias pattern as `mosquitto`/`plex`: the guest that runs it is named `reverse-proxy01` (a generic role name, like `mqtt01`), not `caddy` (the software, like `mosquitto`), so there's no hostname collision and the group can just be called `caddy` directly.
- `technitium: children: [proxmox_tags_technitium]` — same alias pattern as `caddy`/`plex`: the guest that runs it is named `dns01` (a generic role name), not `technitium` (the software), so there's no hostname collision and the group can just be called `technitium` directly.
- `pulse: children: [proxmox_tags_pulse]` — same alias pattern as `caddy`/`plex`/`technitium`: the guest that runs it is named `pulse01`, not `pulse`, so there's no hostname collision and the group can just be called `pulse` directly.

Each playbook then just does `hosts: <group-name>` with no `when:` gate (e.g. `postfix_relay.yaml` → `hosts: postfix_relay`, `nut.yaml` → `hosts: nut`, `update_all_packages.yaml` → `hosts: managed_updates`) — group membership *is* the switch, so there's one source of truth instead of a group plus a flag that could disagree. `timezone.yaml` is the one deliberate exception: it targets `hosts: all` directly rather than a named group in `groups.yaml`, since every host discovered by the dynamic inventory — guest or node, present or future — should be on the same clock with no opt-in step required.

**IPv6 addressing is SLAAC-derived, not Tofu-managed.** Guests don't get an explicit `ip_config.ipv6` block; they pick up an address via SLAAC from router advertisements OPNsense sends on the LAN via its dnsmasq service (which also handles DHCPv4 there — OPNsense's unified DNS/DHCP/RA daemon, not the legacy ISC DHCPD + standalone radvd-style Router Advertisements service), using EUI-64 (interface ID derived from the guest's MAC), which is stable across reboots as long as the guest's `mac_address` is pinned in Tofu (both guests below have theirs pinned specifically for this reason) rather than left to Proxmox to auto-generate. OPNsense's LAN interface still also advertises the real ISP-delegated GUA prefix (via Track Interface, so guests are dual-stacked GUA+ULA), but is now additionally configured with a statically-assigned ULA: `fd01:eae3:bc39::/48` reserved overall, with `fd01:eae3:bc39:100::/64` live on this LAN (gateway at `fd01:eae3:bc39:100::1`) — the ULA is what's meant to be treated as each guest's stable address, since the GUA half still moves if the ISP's delegation ever renumbers. This repo doesn't manage OPNsense, so that config and any DNS AAAA records are set by hand there, outside Ansible/Tofu. Every guest that once had a fixed LAN ULA has since moved to VLAN 50 (see below) — none remain on the LAN today.

Each VLAN gets its own `/64` off the same `/48` (matching the VLAN ID: VLAN 50 → `fd01:eae3:bc39:50::/64`), configured on OPNsense the same by-hand way as the LAN's - OPNsense's actual DNS/DHCP/RA stack is the AdGuard Home plugin, not dnsmasq or ISC DHCPD, and its RA there is in SLAAC-only mode with the RDNSS override pointed at `dns01` rather than OPNsense itself, so VLAN 50 hosts use Technitium as their resolver too. `dns01` (`bc:24:11:7d:cc:f0`) moved off the LAN onto VLAN 50 (`tofu/lxc_dns.tf`'s `network_interface.vlan_id = 50`, static `10.1.50.2/24` since it can't get its own address from a DHCP service it itself provides) to run Technitium as that VLAN's DHCP server (see `technitium_dhcp_scopes` in `ansible/roles/technitium/defaults/main.yaml`) — its ULA there is `fd01:eae3:bc39:50:be24:11ff:fe7d:ccf0`. `pulse01` (`bc:24:11:f7:4b:74`) is also on VLAN 50 (`tofu/lxc_pulse.tf`), but DHCP-addressed rather than static like `dns01` - it has no such chicken-and-egg constraint, so its lease auto-registers in DNS instead (see `dnsUpdates` in the `technitium_dhcp_scopes` note above); its ULA is `fd01:eae3:bc39:50:be24:11ff:fef7:4b74`. `reverse-proxy01` (`bc:24:11:cb:ea:b5`) moved off the LAN onto VLAN 50 too (`tofu/lxc_reverse_proxy.tf`), DHCP-addressed like `pulse01` for the same reason (no chicken-and-egg constraint); its ULA there is `fd01:eae3:bc39:50:be24:11ff:fecb:eab5`. Its former LAN-facing friendly names (`plex.agb.ingenstans.se`, `pve.agb.ingenstans.se`, `pulse.agb.ingenstans.se`) are now CNAMEs to `reverse-proxy01.server.agb.ingenstans.se` (`host_vars/dns01.yaml`) rather than A records pointing at a fixed address, since it no longer has one. `plex01` (`bc:24:11:82:63:3b`) moved the same way; its ULA is `fd01:eae3:bc39:50:be24:11ff:fe82:633b`. `mqtt01` (`bc:24:11:42:31:c4`) moved off the LAN onto VLAN 50 too (`tofu/lxc_mqtt.tf`), DHCP-addressed like `pulse01`/`reverse-proxy01`/`plex01` for the same reason; its ULA there is `fd01:eae3:bc39:50:be24:11ff:fe42:31c4`. Unlike those, mqtt01 isn't fronted by `caddy` (MQTT isn't HTTP) - its `mqtt.hem.ingenstans.se`/`mqtt.k3s.ingenstans.se` names are still hand-managed outside this repo and needed re-pointing there by hand after the move; `mqtt.agb.ingenstans.se` was added as the new friendly name instead, a CNAME into `mqtt01.server.agb.ingenstans.se` (`host_vars/dns01.yaml`), same pattern as the caddy-fronted names above.

One important nameserver gotcha this uncovered: a client on VLAN 50 querying AdGuard Home at OPNsense's LAN address (`10.0.0.1`) gets routed there fine, but AdGuard replies from its VLAN-50-facing address (`10.1.50.1`) instead of the address queried - a UDP DNS client only accepts a reply from the exact address it queried, so this silently drops as a mismatch (looks exactly like a timeout, not a refusal). `dns01`'s own resolver (`tofu/lxc_dns.tf`'s `initialization.dns.servers`) is pinned to `10.1.50.1` for this reason, overriding the datacenter-wide default of `10.0.0.1`.

**Secrets live in `group_vars`, not `defaults`.** Role `defaults/main.yaml` files set non-secret defaults and reference secret variables with `| default(...)` fallbacks; actual secret values are supplied in the relevant role's `inventory/group_vars/<role>.yaml` via 1Password lookups (`op://<vault>/...` — `agb` for the `Proxmox` and `dns` items, `private` for everything else). When adding a new secret-consuming role, follow this pattern (define its group in `groups.yaml`, put its secrets in `group_vars/<role>.yaml`) rather than hardcoding credentials or gating with a boolean var. `plex`'s Samba credentials (username hardcoded to `plex`, password via `op://private/l-space/plex`) follow this exact pattern in `group_vars/plex.yaml` - named after the `plex` group, since `group_vars/<name>` only loads for a group named `<name>` (see below).

**Roles** (`ansible/roles/`):
- `timezone` — sets the system timezone to `Europe/Stockholm` (`timezone_name`) via `community.general.timezone`; applied to every host via `hosts: all` (see above), not a `groups.yaml` group.
- `nut` — configures Network UPS Tools (`nut-server` + `nut-monitor`) for UPS monitoring/shutdown; installs a udev rule for the USB UPS.
- `postfix_relay` — configures Postfix to relay outbound mail through an external SMTP host (`smtp.mailbox.org` by default) using SASL auth.
- `certbot` — installs certbot + the Cloudflare DNS plugin, requests a Let's Encrypt cert per host (`certbot_domains` defaults to `<inventory_hostname>.hem.ingenstans.se`, overridable/extendable per host) via DNS-01 (no port 80/443 exposure needed), then enables certbot's own `certbot.timer` for renewal rather than an Ansible-managed cron job.
- `mosquitto` — installs the Mosquitto MQTT broker with persistence enabled and two listeners: a TLS listener (`mosquitto_tls_port`, default 8883) and a plaintext listener (`mosquitto_plain_port`, default 1883) kept alongside it for units that don't support TLS. Consumes the cert the `certbot` role already requested for this host, but copies it into `/etc/mosquitto/certs` rather than pointing the listener at `/etc/letsencrypt/live/...` directly, since that live path is a symlink into `/etc/letsencrypt/archive`, which is `0700 root` and not traversable by the unprivileged `mosquitto` user. The role also drops its own script into certbot's `/etc/letsencrypt/renewal-hooks/deploy/` so the copy gets refreshed (and mosquitto restarted) after every renewal — `certbot` doesn't need to know mosquitto exists; any future cert consumer plugs into that same hook directory rather than the certbot role growing per-consumer logic. `mosquitto_tls_enabled` derives from `'certbot' in group_names` rather than a separate flag, so a host that isn't in the `certbot` group (no cert to serve) automatically falls back to plaintext-only instead of failing on a missing cert file. Client auth is opt-in via `mosquitto_users` (empty by default), a list of `{username, password}` maps built in `group_vars/mosquitto.yaml` from a single 1Password item ("mqtt-users", a Secure Note) rather than one 1Password item per user like `plex`'s Samba credentials: each user is one custom password-type field on that item, field label as the username and field value as the password, fetched via `community.general.onepassword_raw`, filtered to fields where `type == 'CONCEALED'` and no `purpose` (excludes any built-in fields a non-Secure-Note item type would carry), and turned into the list with `map`/`zip`/`dict`/`dict2items` rather than a Python-style comprehension (Jinja has no such syntax) - adding/removing a user is then a 1Password-only edit, no repo change. No community.general module wraps Mosquitto's own `mosquitto_passwd` CLI tool (it ships with the `mosquitto` package itself, no extra install needed), so the role calls it directly via `command` against a `password_file` (`mosquitto_passwd_file`) - but only for users not already present (checked with a `grep` per user first), since the tool's own hashing is randomly salted PBKDF2-SHA512 and would report changed on every run otherwise; this means a password *rotation* in the 1Password item isn't picked up automatically, only a new user being added. `mosquitto_allow_anonymous` is deliberately kept a manual flag rather than derived from `mosquitto_users` like `mosquitto_tls_enabled` is from group membership: deriving it would lock out any anonymous client the moment the first user is added, so it's left `true` until flipped by hand once every client in use has been migrated to credentials.
- `autologin` — drops a systemd override (`ExecStart=` reset + `agetty --autologin root`) on the guest's tty1 getty unit, restarting it on change so it takes effect without a reboot. Which unit that is depends on guest type (`autologin_getty_unit`, derived from `'proxmox_all_qemu' in group_names` rather than a separate flag, same pattern as `mosquitto_tls_enabled`): LXC containers under systemd use `container-getty@1.service` — what `pct console` attaches to — while QEMU VMs use the plain `getty@tty1.service` a bare-metal host would. Only ever overrides `container-getty@1`/`getty@tty1` (the primary console); other gettys spawned on a guest (e.g. `container-getty@2` for a second configured tty, or `console-getty.service` on LXC's `/dev/console`) are untouched and still prompt for login.
- `unused_services` — disables and stops `cron` and `postfix` on every LXC container (stock Debian template services this stack never uses — mail relaying is `postfix_relay`'s job on `proxmox_nodes`, not here), plus `sshd` unless the guest is tagged `ssh` (`unused_services_keep_ssh`, derived from `'ssh' in group_names` rather than a separate flag, same pattern as `mosquitto_tls_enabled`/`autologin_getty_unit`) — Ansible reaches LXCs via `pct exec`, never SSH, so a listening sshd is unused attack surface by default.
- `plex` — mounts the `//l-space.hem.ingenstans.se/data/media` Samba share read-only at `/mnt/media` (credentials templated into a root-only `/etc/samba/credentials-media` file, referenced from the `_netdev` fstab entry rather than embedded inline), then installs Plex Media Server from its official apt repo (`repo.plex.tv`, signed by the `PlexSign.v2.key` - the original `downloads.plex.tv`/`PlexSign.key` pairing is deprecated and its key carries a SHA1 binding signature that Debian trixie's `sqv` verifier rejects under the post-2026-02-01 crypto policy) via `deb822_repository` (key fetched straight from `plex_apt_key_url` and dearmored by the module itself, no manual `gpg --dearmor` step), and enables/starts the `plexmediaserver` service. No config templating for Plex itself: it's set up and claimed through its own web UI, not a static config file Ansible would own.
- `caddy` — reverse proxy for web UIs on non-standard ports, installed from Caddy's official apt repo (`dl.cloudsmith.io/public/caddy/stable`, same `deb822_repository` pattern as `plex`). Routes are driven entirely by `caddy_proxies`, a list of `{hostname, backend, backend_scheme, backend_tls_insecure}` maps supplied per host (`host_vars/reverse-proxy01.yaml`), templated into one vhost block per entry in `/etc/caddy/Caddyfile`; `backend_scheme`/`backend_tls_insecure` exist because some backends (e.g. Proxmox's own web UI on 8006) are HTTPS-only with a self-signed cert, unlike the plain-HTTP default. Consumes a single wildcard cert (`certbot_domains: ["hem.ingenstans.se", "*.hem.ingenstans.se"]`, overridden in `host_vars/reverse-proxy01.yaml` since the role default is one name per host) covering every vhost it fronts, copied into `/etc/caddy/certs` and refreshed via a certbot renewal hook — the same cert-handoff pattern `mosquitto` uses, chosen so adding a new proxied hostname is just a `caddy_proxies` edit, never a cert request. The guest itself is named `reverse-proxy01` rather than `caddy`, following the `mqtt01`/`mosquitto` split (generic role name for the host, software name for the tag/group) — see `caddy` in `groups.yaml` above.
- `technitium` — installs Technitium DNS Server by fetching and running its official install script (`technitium_install_script_url`, `download.technitium.com/dns/install.sh`) rather than the `deb822_repository` pattern `plex`/`caddy` use, since Technitium doesn't publish an apt repo. The script is re-run unconditionally on every play (`force: true` on the `get_url`, no `creates` guard on the `command`) rather than gated on a one-time install check, because Technitium's own docs treat re-running this same script as the update mechanism: it always pulls the latest DNS server tarball, and once `/etc/dns/config` exists it just re-extracts, re-`chown`s, and `systemctl restart dns.service`s, skipping the one-time `useradd`/systemd-unit/`NetworkManager` setup from a fresh install. There's no version file or diffing in the script (or anywhere else) to check "is a newer release available" without actually re-running it, so every play run restarts `dns.service` regardless of whether a new version actually shipped — the cost of upgrades actually flowing through the playbook rather than needing a manual login to the web console. The guest is named `dns01` rather than `technitium`, following the `mqtt01`/`mosquitto` split — see `technitium` in `groups.yaml` above. `dns01` is still tagged `managed-updates` like every other guest: that only covers apt-based OS package bumps via `update_all_packages.yaml`, a separate channel from Technitium's own version, which is upgraded by this role on every play. Unlike `plex`, zone/record data *is* Ansible-managed here — DNS was judged too important to leave to manual console edits. The role uses the third-party `effectivelywild.technitium_dns` collection's state-based `technitium_dns_zone`/`technitium_dns_record` modules (idempotent `state: present`/`absent`, not the collection's other imperative `create_zone`/`add_record`-style modules) against Technitium's REST API on `localhost:5380` (tasks run on `dns01` itself via `pct exec`, so `localhost` always resolves correctly regardless of the guest's LAN address). Desired zones/records are supplied per host in `host_vars/dns01.yaml` as `technitium_zones`/`technitium_records` lists of arbitrary API-param maps, merged over `{api_url, api_token, state: present}` defaults with `combine` in `tasks/main.yaml` rather than the role enumerating every record type's fields itself — the same "let the caller's dict shape drive the module call" approach as `caddy_proxies`, chosen because the record module alone has ~30 type-specific optional params (`ipAddress`, `cname`, `exchange`, ...). Authentication is a pre-generated API token (`technitium_api_token`), not a username/password the role logs in with — generate it once via the web console (Administration > Sessions > Create Token) and store it in 1Password, since this repo's convention is that Ansible consumes pre-existing secrets, never generates them itself.

`dns01` is also tagged `certbot` (`tofu/lxc_dns.tf`) so Technitium can terminate TLS itself rather than sitting behind `caddy` the way every other web UI here does: DNS-over-TLS is raw TLS-wrapped DNS on its own port, not HTTP, so a reverse proxy in front of it couldn't terminate it anyway, and once Technitium needs its own cert for that, the web console piggybacks on the same one instead of splitting TLS termination across two different services. `host_vars/dns01.yaml` overrides `certbot_domains` to cover both names dns01 is reachable as: the friendly `dns.agb.ingenstans.se` (hardcoded rather than built from `inventory_hostname` — same generic-service-name-vs-host-name split as `caddy`/`reverse-proxy01` and `plex`/`plex01` — and the one `technitium_domain` points `--cert-name`'s lineage at) and `dns01.server.agb.ingenstans.se` (its own already-existing static record), ahead of the certbot role's plain `dns01.hem.ingenstans.se` default — matching `reverse-proxy01`'s earlier move to the newer domain. Both validate through the same Cloudflare DNS-01 challenge even though only `agb.ingenstans.se`, not `server.agb.ingenstans.se`, is a zone Cloudflare actually hosts: `dns01.server.agb.ingenstans.se` is still a subdomain *of* `agb.ingenstans.se`, and nothing delegates `server.agb.ingenstans.se` away from Cloudflare (see its "no NS delegation needed" zone comment), so Cloudflare remains the public authority for that name too and can place the challenge TXT record under it like any other subdomain. That's the split-horizon property the whole setup relies on: Cloudflare stays authoritative for the public DNS-01 lookup across all of `agb.ingenstans.se`, while the same-named Primary zone inside Technitium (`technitium_zones` below) independently serves different, internal-only answers for specific names — the two are resolved through entirely separate paths (Cloudflare's public nameservers vs. Technitium's API) and never conflict. A `dns.agb.ingenstans.se` CNAME (`technitium_records`, into `dns01.server.agb.ingenstans.se`) makes the friendly name resolve internally too, same pattern as the `plex`/`pve`/`pulse` friendly names. Technitium takes its cert as a single PKCS#12 (`.pfx`) bundle rather than the separate `fullchain.pem`/`privkey.pem` copies `mosquitto`/`caddy` use, so a `command`-run `openssl pkcs12 -export` (no `creates` guard, same reasoning as certbot's own cert-request task) rebuilds it from certbot's live PEM output on every play, and a certbot deploy hook rebuilds it again on renewal. The `.pfx` password (`technitium_pfx_password`) is deliberately hardcoded empty rather than pulled from 1Password: the file is only ever read by Technitium's own `dns-server` service user off a `0600` path, so the filesystem permissions are what actually protect it, the same as `mosquitto`/`caddy`'s unencrypted private key copies — PKCS#12 just requires *a* password syntactically. `technitium_dns_set_server_settings` then points the web console (`webServiceTlsPort`, 53443) and both DNS-over-TLS (853) and DNS-over-HTTPS (443) at that same bundle in one API call, plus turns on `dnssecValidation` so Technitium validates DNSSEC on the upstream/recursive answers it forwards. Zone signing is separate from that call: `technitium_dns_sign_zone` "will not update DNSSEC properties once initially signed" and errors on a zone that's already signed, so the role first calls `technitium_dns_get_dnssec_properties` per zone in `technitium_dnssec_zones` (`host_vars/dns01.yaml`) and only signs the ones still `Unsigned` — ECDSA/P256 by default, chosen as the modern, widely-supported, low-overhead choice over RSA. `hem.ingenstans.se` is deliberately left unsigned (it's being retired, per the zone comment in `host_vars/dns01.yaml`); none of the signed zones are delegated to `dns01` from a real parent zone (they're all internal-only), so signing them doesn't build a chain of trust an external resolver could follow — its value here is a validating client on the LAN/VLAN 50 being able to detect a tampered/spoofed answer, not public verifiability. `tofu/firewall_dns.tf` locks `dns01` down to a default-deny inbound Proxmox firewall (it previously had none at all, unlike `pulse01`'s) with explicit allows for plain DNS (53), DNS-over-TLS (853), DNS-over-HTTPS (443), and the web console (53443) from the LAN and VLAN 50, plus DHCP relay (67) narrowed to OPNsense's VLAN 50 interface address specifically — unlike `pulse01`'s single-consumer dashboard rule, the DNS/web console rules admit whole subnets since any LAN/VLAN 50 client is a legitimate caller, and the console isn't narrowed to a specific admin source the way `pulse01`'s is because Technitium's console is authenticated (that rule exists to compensate for Pulse having none).
- `pulse` — installs Pulse (rcourtman/Pulse, a Proxmox/Docker/Kubernetes monitoring dashboard) via its official install script (`pulse_install_script_url`, `raw.githubusercontent.com/rcourtman/Pulse/main/install.sh`), guarded by a `stat` check on `/bin/update` so it only runs on a genuinely fresh install, unlike `technitium`'s unconditional-rerun pattern. Re-running is deliberately *not* how this role keeps Pulse current: `/bin/update` prompts via `/dev/tty` directly (bypassing stdin redirection entirely) whenever it's ambiguous whether to reinstall an already-up-to-date install, and since `pct exec` always provides a real pty, that read never gets an EOF and just hangs forever with no flag to force past it - unlike Technitium's install script, which has no such interactive case. Pulse's own installer already sets up a `pulse-update.timer` (daily, 2-6 AM) that keeps it current on its own, so this role leans on that instead - the same "install once, let the software's own timer own renewal" shape `certbot` uses in this repo. The installer's own defaults (service name `pulse`, port 7655) are used as-is, no config templating. Previously run by hand directly on `pve1` rather than in a dedicated guest; moved into its own LXC (`pulse01`, VLAN 50, DHCP-addressed) both to bring it in line with every other service here and because giving something running directly on the hypervisor a VLAN address would mean tagging `pve1`'s own host networking, which risks its management connectivity - a guest is the safe way to get a service onto a given VLAN.

`nut`, `postfix_relay`, `mosquitto`, `autologin`, and `caddy` follow the same shape: `defaults/main.yaml` (config vars), `tasks/main.yaml` (install package → template configs, each notifying a handler → enable/start service), `handlers/main.yaml` (restart-on-change), `templates/*.j2` (config files rendered from vars). `pulse` has a handler (`Restart Pulse`, notified when its `/etc/pulse/.env` override changes - e.g. `PULSE_TELEMETRY=false`) but no templates: that file is a single `lineinfile` edit into a hook the installed unit already provides (`EnvironmentFile=-/etc/pulse/.env`), not a Jinja template Ansible owns the whole content of. `certbot`, `unused_services`, `plex`, `technitium`, and `timezone` have no handler or templates: `certbot` because nothing needs restarting on cert issuance/renewal (the standalone timer owns renewal); `unused_services` because it only flips `state`/`enabled` on services that are already installed by the base template, with nothing to render; `plex` because there's no Ansible-managed config file to change, just an install step and a service enable; `technitium` because its zone/record state lives behind a REST API, not a config file Ansible would template and reload; `timezone` because it's a single module call with no config file or service to restart.

## OpenTofu (`tofu/`)

Provider: `bpg/proxmox`, authenticating with its own `root@pam!opentofu` API token — separate from the `root@pam!ansible` token the Ansible inventory uses, so the two tools don't share credentials (same Proxmox host, `pve1.hem.ingenstans.se`). Run commands from `tofu/`:

```bash
op run --env-file .env -- tofu plan
op run --env-file .env -- tofu apply
```

`tofu/.env` (gitignored) holds `TF_VAR_proxmox_token_secret=op://agb/Proxmox/opentofu-api-token` (a field on the same `Proxmox` 1Password item Ansible's secrets live on, alongside `ansible-api-token`). `provider.tf` builds the full `api_token` string (`user!tokenid=secret`) from that var; only the secret half is out of tree.

The `opentofu` token needs more than the `PVEAdmin` role: any resource that downloads by URL (e.g. `proxmox_download_file`, used for CT templates) calls Proxmox's `query-url-metadata` endpoint, which requires `Sys.AccessNetwork` — not covered by `PVEAdmin` or any built-in role short of full `Administrator`. Granted narrowly instead: a custom `AccessNetwork` role (just `Sys.AccessNetwork`) assigned to the token on `/nodes` (propagated, so it covers `pve1` and any future node) rather than handing out `Administrator` on `/`.

State is local (`terraform.tfstate`, gitignored) — deliberate for a single-operator, single-machine homelab: local state avoids standing up a remote backend to solve a locking problem that doesn't exist here. The tradeoff is that state isn't backed up independently of this repo's `tofu/` directory; if this machine is lost with no backup, the Proxmox resources OpenTofu created keep running untouched, but reattaching them requires `tofu import` per resource. `.terraform.lock.hcl` **is** committed (pins provider version/hashes); `.terraform/` and `*.tfstate*` are not.
